================================================================================
第一部分：死亡与尸体系统
================================================================================

【设计总则】
死亡是AHEI生命周期的终点。它不是预设的“游戏结束”触发，
而是生理系统（文档2）在物理环境（文档5-7）中长期运行后
自然抵达的终点。尸体的存在不是瞬间消失，而是作为物理实体
继续存在于世界中，经历完整的腐败过程，并对周围的环境和
AHEI种群产生持续的影响。


第一章  死亡判定
================================================================================

1.1 死亡原因总表

    AHEI的死亡由以下任一条件触发。所有判定由Python端的
    生理系统（physiology_engine.py）在每帧检查。

| 死亡原因 | 判定条件 | 是否可避免 | 相关文档 |
|---------|---------|-----------|---------|
| 饥饿死亡 | energy归零且持续30秒未进食 | 是，及时进食 | 文档2第五章 |
| 外伤死亡 | health归零（任何外伤累积） | 是，及时治疗 | 文档2第八章 |
| 失血死亡 | 失血量>60%（约40秒严重流血未止血） | 是，及时止血包扎 | 文档2第八章8.4节 |
| 中毒死亡 | toxin_level持续过高无法代谢 | 是，服用解毒草药或强免疫力 | 文档2第六章6.3节 |
| 溺水死亡 | 水下窒息超过90秒 | 是，及时浮出水面 | 文档2第十章 |
| 高温死亡 | 体温>42°C持续过久 | 是，及时降温 | 文档2第十章10.3节 |
| 低温死亡 | 体温<30°C持续过久 | 是，及时取暖 | 文档2第十章10.3节 |
| 坠落死亡 | 从>20米坠落（头着地则>5米即可致命） | 是，避免高处坠落 | 文档2第八章8.9节 |
| 衰老死亡 | age达到lifespan_max | 否（除非被设置为不衰老） | 文档2第三章 |
| 疾病死亡 | 感染未被免疫系统击败 | 是，提高免疫力或用药 | 文档2第七章 |
| 窒息死亡 | 缺氧环境（洞穴深处/密闭空间） | 是，及时离开缺氧区域 | 文档2第十章 |
| 挤压死亡 | 被极重物体持续挤压>5分钟 | 是，移开重物或逃脱 | 文档2第八章8.10节 |

1.2 死亡瞬间的生理与认知变化

    当AHEI的health归零或满足其他死亡条件时，
    以下变化在Python端和Godot端同时发生：

    Python端（生理系统）：
        1. 所有生理变量（energy, health, hydration等）冻结在最终值
        2. 大脑（预测编码网络）停止计算
        3. 记忆系统保留所有已存储的记忆条目，
           但不再接收新记忆
        4. 死亡事件以emotional_tag=-0.95被写入邻近AHEI的长期记忆
        5. 生理系统向Godot端发送death事件：
           {"type":"death","ahei_id":"A001","cause":"blood_loss","time":12345.6}

    Godot端（表现层）：
        1. AHEI_Body节点的CharacterBody3D被替换为RigidBody3D
           （尸体是纯物理刚体，不再主动运动）
        2. 所有MotorJoint脚本被禁用（尸体不再主动运动）
        3. 身体材质颜色在0.5秒内从正常肤色过渡为灰白色
           （饱和度降至0，亮度降低30%）
        4. 尸体倒向受力方向或自然倒下（ragdoll效果）
        5. 尸体节点被标记为corpse类型，添加腐败计时器
        6. 尸体挂载SmellComponent，开始散发微弱气味

1.3 死亡在Python端和Godot端的处理流程

    Python端处理流程：
        1. 生理系统检测到死亡条件满足
        2. 广播death事件到以下模块：
            - 记忆系统：将死亡事件写入死者自身的长期记忆
            - 演化系统：记录死亡时间和原因，用于后续适应度计算
            - 生态系统：减少AHEI种群计数
        3. 向Godot端发送death事件（含位置、姿态、死亡原因）

    Godot端处理流程：
        1. 接收death事件
        2. 执行1.2节描述的视觉和物理变化
        3. 将尸体注册到WorldManager的corpse_list中
        4. 启动腐败计时器
        5. 向附近AHEI发送social_event："observed_death"


第二章  尸体的物理与视觉表现
================================================================================

2.1 尸体节点的创建与物理属性

    尸体不是重新创建的节点，而是AHEI_Body节点的状态转换。
    
    物理属性变化：
        - 节点类型：CharacterBody3D → RigidBody3D
        - 质量：保持不变（继承死者生前的体重）
        - 碰撞体：保持不变（但不再主动避开障碍物）
        - 摩擦系数：从0.6降至0.5（皮肤失去弹性）
        - 弹性：从0.3降至0.1（肌肉松弛）
        - 重心：保持不变（但失去主动平衡能力）

    视觉属性变化：
        - 肤色：0.5秒内从正常肤色过渡为灰白色
          （Godot实现：使用Tween将material的albedo_color
           饱和度从正常值过渡到0，亮度降低30%）
        - 眼睛：虹膜颜色保持不变，但眼睑闭合（模拟死亡后的眼部放松）
        - 嘴巴：微微张开（模拟下颌肌肉松弛）
        - 整体外观：身体姿势由重力自然决定（ragdoll）

2.2 尸体腐烂的五个阶段

    尸体在世界中经历完整的腐败过程，每个阶段有独特的视觉、
    气味和物理特征。

| 阶段 | 时间（游戏内） | 视觉表现 | 气味强度 | 物理变化 | 可获取资源 |
|------|--------------|---------|---------|---------|-----------|
| 新鲜 | 0-2分钟 | 灰白色，外观完整 | 1/10 | 刚体，可拖动 | 完整兽皮、肉、骨骼 |
| 膨胀 | 2-5分钟 | 腹部微胀，皮肤出现暗斑 | 3/10 | 体积微增5% | 肉（品质下降） |
| 活跃腐败 | 5-8分钟 | 皮肤变黑，体液渗出 | 7/10 | 质量减少10% | 骨骼、角、牙齿 |
| 白骨化 | 8-10分钟 | 仅剩骨骼 | 3/10 | 质量减少80% | 骨骼、角、牙齿 |
| 完全分解 | 10分钟后 | 实体被queue_free() | 0 | 无 | 无 |

    时间基数为游戏内时间。时间流速受GameState.time_ratio影响。
    在1:1时间比下，尸体在真实世界10分钟内完全分解。
    在加速模拟中（如3600:1），尸体在约0.17秒内完成分解。

    Godot实现：
        尸体节点挂载一个DecompositionTimer脚本，
        每游戏秒更新一次腐败阶段。
        每个阶段的转换通过Tween平滑过渡视觉表现。

    ```gdscript
    # DecompositionTimer.gd
    extends Node
    
    var elapsed_game_seconds: float = 0.0
    var current_stage: String = "fresh"
    
    const STAGES = [
        {"name": "fresh", "duration": 120.0, "odor": 1, "color": Color(0.7, 0.7, 0.7)},
        {"name": "bloat", "duration": 180.0, "odor": 3, "color": Color(0.5, 0.5, 0.4)},
        {"name": "active_decay", "duration": 180.0, "odor": 7, "color": Color(0.2, 0.2, 0.1)},
        {"name": "skeletal", "duration": 120.0, "odor": 3, "color": Color(0.9, 0.9, 0.85)},
    ]
    
    func _process(delta: float) -> void:
        elapsed_game_seconds += delta * GameState.time_ratio
        _update_stage()
    ```

2.3 尸体对环境的物理影响

    尸体不仅是视觉元素，还会对环境产生以下物理影响：

    - 拖动：尸体可以被AHEI或其他动物拖动，
      这由RigidBody3D的物理引擎自动处理
    - 压坏植被：尸体落在小型植物上会破坏植物节点
    - 水源污染：尸体在水中腐烂时，周围水体的
      contamination_level上升，饮用污染水可能导致疾病
    - 吸引食腐动物：尸体气味吸引捕食者和食腐动物，
      增加尸体附近区域的捕食者密度
    - 养分回归：尸体完全分解后，该位置的土壤肥力
      临时提升30%，持续约30游戏天，促进植物生长


第三章  尸体的社会影响
================================================================================

3.1 同伴发现尸体的行为反应

    AHEI发现尸体时的行为反应由Python端的情感系统、
    镜像神经元系统和记忆系统共同驱动。
    反应强度取决于发现者与死者的社会关系。

| 关系类型 | 行为表现 | 生理变化 | 持续时间 |
|---------|---------|---------|---------|
| 完全陌生 | 短暂警戒→继续原本行为 | 预测误差微升（0.1→0.3），快速恢复 | 5-10秒 |
| 认识但不熟 | 停留5-10秒→可能发出低频声音→离开 | 血清素微降0.1，预测误差升高至0.5 | 30-60秒 |
| 朋友/同盟 | 长时间停留→推碰尸体→发出哀鸣→可能守夜数分钟 | 催产素下降0.3，血清素下降0.3 | 数分钟 |
| 伴侣 | 崩溃式哀悼→守尸→拒绝进食→可能因衰弱而死亡 | 催产素骤降0.7，血清素骤降0.5 | 数小时，甚至导致死亡 |
| 母亲→幼崽尸体 | 抱起尸体→连续哀鸣→长时间守夜→攻击任何靠近者 | 催产素骤降0.8，攻击性飙升 | 数小时至数天 |
| 幼崽→母亲尸体 | 催产素骤降→寻找替代依恋对象→可能被其他成年雌性收养 | 血清素持续偏低，恐惧基线升高 | 数天至数周 |

    这些反应不是预设的脚本，而是从文档4第一章描述的情感系统中
    自然涌现的。详见文档4第一章1.3节（复杂社会情感）和
    文档4第六章（育幼与依恋）。

3.2 哀悼与葬礼的涌现

    AHEI没有预设的“葬礼仪式”。但当一群AHEI反复观察
    到尸体被食腐动物撕裂、或被腐烂气味困扰后，
    某些个体可能开始执行以下行为：

    第一，拖走尸体。
    某AHEI可能将尸体拖到远离巢穴和水源的地方，
    最初动机是防止气味吸引捕食者。
    经过多代观察和模仿，这种行为可能成为
    群体对待尸体的默认方式。

    第二，覆盖尸体。
    某AHEI可能用石头、树枝或泥土覆盖尸体，
    最初动机可能是防止食腐动物啃食。
    覆盖行为在功能上等同于最原始的“埋葬”。

    第三，守夜行为。
    与死者有强烈依恋关系的AHEI，
    可能在尸体旁守夜数小时甚至数天。
    守夜行为不是仪式，而是依恋系统驱动下的
    自然反应——依恋对象消失了，
    守夜者无法离开。

    第四，骨头的特殊对待。
    某些部落可能开始收集死亡个体的骨骼，
    存放在特定位置（如洞穴深处的“墓地”）。
    这种行为的涌现需要数百代的演化。

    如果AI教师在部落中，它可能通过故事化的方式
    引导AHEI如何体面地处理同伴的尸体——
    但这发生在AHEI与AI教师长期互动之后，
    不是预设的。

3.3 尸体的记忆留存与文化影响

    尸体的视觉、气味和位置信息会以高情绪标签
   （emotional_tag约-0.7到-0.9）刻入发现者的长期记忆。

    记忆留存的效果：
        - 发现者未来经过同一地点时，
          大脑会自动检索到此次尸体发现记忆，
          预测误差提前升高，恐惧基线抬高
        - 如果死者是部落中的重要成员（如首领、工匠），
          其死亡地点可能成为群体口述中的“纪念地”
        - 如果死亡事件被反复在群体中讲述，
          它可能演变为部落的“集体记忆”——
          这为后来的“祖先崇拜”或“英雄传说”提供了认知基础

    AI教师可能通过故事化的方式（详见文档9第十二章），
    将某个重要个体的死亡编织为“英雄的传说”——
    但AI教师不会承认自己是故事的创作者，
    而是以“我听说过……”的方式引入。

第二部分：开发调试与日志系统
================================================================================

【设计总则】
以下系统为开发阶段的辅助工具，不直接影响AHEI的模拟逻辑。
调试面板帮助开发者在运行时查看AHEI的内部状态、
手动触发事件、或在步进模式下逐帧分析行为。
日志系统记录所有关键事件，支持后续的量化和回溯分析。
行为回放系统允许开发者以任意速度回放已记录的演化历史。


第四章  开发者调试面板
================================================================================

4.1 打开方式与总体布局（F3键）

    按F3键打开开发者调试面板。与全知面板（G键）不同，
    调试面板面向开发者，显示更深层的技术数据。

    面板布局：
    DebugPanel (Control, process_mode = always)
    ├── TabContainer
    │   ├── [感官] 标签页
    │   │   └── 实时显示当前选中AHEI的60维感官向量
    │   ├── [大脑] 标签页
    │   │   └── 神经网络各层权重分布直方图
    │   ├── [事件] 标签页
    │   │   └── 手动触发事件的按钮列表
    │   ├── [步进] 标签页
    │   │   └── 暂停/单帧/恢复控制
    │   └── [性能] 标签页
    │       └── 实时FPS、GPU/CPU/内存占用

4.2 感官向量实时显示

    在[感官]标签页中，当前选中AHEI的60维感官向量
    以60个进度条（HSlider）的形式实时显示。
    每维标注其名称和当前值。

    维度分组显示：
        - 视觉(21维)：射线0距离、类型、灰度；射线1……
        - 听觉(5维)：基频、频谱重心、频谱宽度、水平角、垂直角
        - 触觉(7维)：碰撞力、部位编码×3、方向、损伤强度、损伤类型
        - 嗅觉(2维)：食物方向×2
        - 味觉(5维)：甜、苦、酸、咸、鲜
        - 生理(6维)：能量、健康、水分、体温、疲劳、激素
        - 本体(12维)：头、左臂、右臂、左腿坐标
        - 前庭(2维)：倾斜度、摔倒标志

    开发者可以通过观察感官向量各维度的变化，
    定位AHEI行为异常的来源。
    例如，如果AHEI持续走向危险区域，
    可能是因为视觉向量中“捕食者”类型编码被错误识别。

4.3 神经网络可视化

    在[大脑]标签页中，当前选中AHEI的预测编码网络
    各层权重以直方图形式显示。

    可视化内容：
        - 每层权重的分布直方图（均值、标准差标注）
        - 每层偏置的分布直方图
        - 预测误差的实时折线图（最近60秒）
        - 行动概率的实时柱状图（8个行动选项）

    用途：
        - 检测梯度消失/爆炸（权重分布过窄或过宽）
        - 检测过拟合（权重分布出现极端值）
        - 检测行为固化（行动概率集中在一个选项上）

4.4 手动事件触发

    在[事件]标签页中，开发者可以手动触发特定事件，
    以测试AHEI或系统的响应。

    可触发事件列表：
        - 天气事件：强制下雨、强制暴风雪、强制山火、强制洪水
        - 资源事件：在指定位置投放食物、在指定位置投放捕食者
        - 社交事件：强制两个AHEI交配、强制生成新生儿、
                    强制AHEI死亡
        - 演化事件：强制种群演化一代、强制刷新所有AHEI状态
        - 模组事件：重新加载所有模组

    每个事件按钮旁边有参数输入框，
    允许指定事件的位置、目标AHEI、强度等参数。

4.5 步进模式

    在[步进]标签页中，开发者可以暂停模拟，
    然后以单帧为单位推进。

    控制按钮：
        - [暂停/恢复]：切换模拟的暂停状态
        - [单帧前进]：模拟推进一个物理帧（约1/60秒）
        - [单秒前进]：模拟推进一秒（60帧）
        - [跳转到下一事件]：自动快进到下一个关键事件
          （如AHEI进食、受伤、死亡）

    步进模式对于调试复杂的交互逻辑
   （如同步问题、碰撞检测bug）至关重要。

4.6 性能监控

    在[性能]标签页中，实时显示以下指标：

        - FPS：当前帧率
        - GPU占用：当前GPU利用率百分比
        - CPU占用：当前CPU利用率百分比
        - 内存：当前内存使用量（MB）
        - 实体数量：当前场景中的总实体数
        - AHEI数量：当前存活的AHEI数量
        - 每帧感官采集耗时：SensoryCollector的平均耗时（毫秒）
        - 每帧大脑推理耗时：Python端预测编码网络的平均耗时（毫秒）
        - WebSocket延迟：Godot与Python之间的通信延迟（毫秒）

    这些指标帮助开发者在性能出现瓶颈时
    快速定位问题来源。


第五章  日志系统
================================================================================

5.1 日志存储格式

    所有关键事件以JSON Lines格式存储。
    每行一个JSON对象，存储在 `logs/events.jsonl`。

    日志条目示例：
    ```json
    {"type":"birth","time":12345.6,"ahei_id":"AHEI_0247","parent_ids":["AHEI_0103","AHEI_0082"]}
    {"type":"death","time":12350.2,"ahei_id":"AHEI_0091","cause":"predator_attack","location":[12.3,45.6,-78.9]}
    {"type":"eat","time":12352.0,"ahei_id":"AHEI_0105","food_type":"berry","amount":15}
    {"type":"discovery","time":12355.0,"ahei_id":"AHEI_0105","discovery":"smelting_copper"}
    {"type":"mating","time":12360.0,"male_id":"AHEI_0105","female_id":"AHEI_0082","conception":true}
    ```

5.2 事件类型分类

| 事件类型 | 触发条件 | 日志字段 |
|---------|---------|---------|
| birth | 新生儿诞生 | ahei_id, parent_ids, time, location |
| death | AHEI死亡 | ahei_id, cause, time, location |
| eat | AHEI进食 | ahei_id, food_type, amount, time |
| discovery | AHEI发现新知识 | ahei_id, discovery, time |
| mating | 交配成功 | male_id, female_id, conception, time |
| injury | AHEI受伤 | ahei_id, injury_type, severity, time, location |
| crafting | 制作物品 | ahei_id, item_type, method, time |
| building | 建造完成 | ahei_id, building_type, time, location |
| tribe_formation | 新部落形成 | tribe_name, member_ids, time |
| tribe_conflict | 部落冲突 | tribe_a, tribe_b, outcome, time |
| weather_event | 极端天气 | weather_type, severity, time |
| ai_teacher_interaction | AI教师教学 | teacher_id, student_id, topic, time |

5.3 日志过滤与查询

    日志系统提供以下查询功能：

    - 按时间范围过滤（如：查看第100-200代的所有事件）
    - 按事件类型过滤（如：只查看death事件）
    - 按实体ID过滤（如：查看AHEI_0105的一生经历）
    - 按位置过滤（如：查看坐标(10,20)附近的所有事件）
    - 组合查询（如：第100-200代中，所有因predator_attack死亡的事件）

    Godot端和Python端均可查询日志。
    Python端通过在brain_server.py中读取logs/events.jsonl文件实现。
    Godot端通过HTTP请求向Python端发送查询。

5.4 日志的存储与清理策略

    - 日志文件位置：世界文件夹的logs/目录下
      （如：MyWorld/logs/events.jsonl）
    - 日志文件大小：典型运行100代约产生5000-10000条事件，
      文件大小约1-2MB
    - 自动清理：当日志文件超过100MB时，
      自动将旧日志归档为events_archive_YYYYMMDD.jsonl.gz
    - 手动导出：在全知面板中点击“导出日志”按钮，
      将当前日志导出为CSV文件供外部分析


第六章  行为回放系统
================================================================================

6.1 回放数据的存储与加载

    回放数据由两部分组成：
        1. 世界初始状态（世界种子 + 种群初始基因组）
        2. 事件日志（记录了所有影响模拟状态的关键事件）

    回放系统通过以下步骤重现一段演化历史：
        1. 加载世界初始状态（按世界种子重新生成地形）
        2. 按事件日志的时间线，
           在对应时间点重新执行每个关键事件
        3. AHEI的行为在两次事件之间通过
           预测编码网络的确定性计算来推断

    注意：由于预测编码网络的行为在相同输入下是确定的，
    回放可以精确还原AHEI的所有行为——
    不需要存储每一帧的状态。

6.2 回放速度控制

    回放速度可控：
        - 0.1x：慢速回放（用于观察AHEI的细微行为变化）
        - 1x：正常速度
        - 10x：快速回放（用于快速浏览长时间跨度）
        - 100x：极速回放（用于定位特定事件）
        - 跳转到事件：直接跳转到指定的日志事件

    回放速度控制通过GameState.time_ratio临时调整，
    不影响世界存档的实际时间。

6.3 回放中的视角切换

    在回放模式下，视角可以在以下模式间切换：
        - 观察者模式：自由飞行摄像机
        - 追踪模式：摄像机绑定到特定AHEI（追踪其一生）
        - 事件中心模式：摄像机自动定位到每个关键事件的发生位置

6.4 回放数据与存档的区别

    回放数据不是世界存档的替代品。
    
    世界存档（.sav）存储的是某个时间点的完整世界状态。
    回放数据（事件日志+世界种子）存储的是“如何从初始状态
    到达某个状态”的完整过程。

    回放数据的优势：
        - 文件极小：100代的回放数据约1-2MB
        - 可分析：事件日志可以直接导入Excel或Python进行分析
        - 可复现：相同的世界种子+相同的事件日志，
          在相同版本的代码下产生完全一致的结果

    回放数据的局限：
        - 如果代码版本不同，回放可能产生偏差
        - 如果使用了随机判定（如交配成功概率），
          回放需要在日志中额外记录随机数种子
